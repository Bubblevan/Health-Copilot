# H-Ref Adoption Decisions and Research Relevance

This is a design-review record, not a feature backlog. The source identities are pinned in [`source_manifest.json`](source_manifest.json); the repository maps and matrix contain the detailed source paths and symbols. No decision below authorizes a change to frozen M0–M10.1 or E0/E0.1 behavior.

## Decision rule

`ADOPT_NOW` requires an observed Health failure or imminent E2–E5 requirement, an insufficient current abstraction, preserved safety/replay/eval invariants, deterministic testability, and no motivation other than upstream precedent. No candidate met all five conditions in this read-only audit.

## Complexity audit: abstractions to watch in Health

The following are review findings, not refactor instructions.

| Area | Evidence | Risk | Recommendation |
| --- | --- | --- | --- |
| Profile and component identity | `RuntimeProfile`, `ComponentManifest`, `RuntimeComponents` and `RuntimeBuildConfig` all carry related identity/config fields (`runtime/profile.py`, `runtime/components.py`, `runtime/builder.py`). | A future change could accidentally hash mutable state or duplicate ownership of component identity. | Keep profile selection, build manifest, and run metadata as separate roles; add no fourth identity layer without a failing case. |
| Session/context/memory lifetime | `AgentSession`, `SessionStore`, `ContextPlan`, `MemorySnapshotIdentity` and `RunContext` are intentionally separate but cross-reference each other. | Callers may read a run-local object as durable state or use a plan hash without its full state tuple. | Preserve the existing state-plane table; require state tuple comparison in replay tests. |
| Tool policy layering | `EvidencePolicy`, `ToolRunner`, `PermissionGuard`, `SandboxBackend` and MCP adapter each own a different decision. | A new generic middleware layer could obscure which policy is authoritative. | Add a new seam only with an owner, failure code and deterministic test; do not merge policies by naming similarity. |
| Evaluation and runtime registries | `EvalSuiteRegistry` is separate from `ComponentRegistry` by design (`docs/architecture.md`, `eval/registry.py`). | An abstraction that unifies them could let benchmark code select runtime capabilities or let runtime code mutate gold semantics. | Keep the registries separate and document cross-reference IDs only. |
| Team orchestration | `team.py` contains task, mailbox, lead, worker, ledger, budget and failure types. | E2 could add another orchestration layer beside M8 before an empirical question is fixed. | Treat the current M8 topology as a baseline and create a research-only adapter only after E1/E2 gate evidence. |
| One-implementation protocols | `ContextProjector`, `ProviderExecutor`, `MemoryStore`, `SessionStore`, `SandboxBackend` and policy protocols often have one production implementation plus test doubles. | Interfaces may be mistaken for proof of extensibility or multiplied without a second semantic implementation. | Retain a protocol when it defines a test/replay/security boundary; otherwise measure before adding another abstraction. |
| Error translation | Runtime, M10, MCP, team and eval layers each translate failures into their own typed outcomes. | Generic catch-and-wrap can erase whether the failure happened before safety, during projection, at commit, or during provider execution. | Keep stage-specific error codes and assert the stage in offline tests. |

## E2 relevance

The most material E2 primitives are child capability scopes, parent cancellation/budget propagation, typed lifecycle events, telemetry parentage, and failure containment. Pi contributes explicit Context and operation lifecycle; DSH contributes scoped registrations, child composition and durable policy events. Health already has the more important medical controls: shared EvidencePolicy, KnowledgeScope, ToolRunner, parent budget, isolated worker sessions, and deterministic ledger provenance. The correct E2 question is therefore whether a bounded scope/lifecycle adapter improves heterogeneous worker attribution and failure recovery—not whether Health should become a general plugin runtime.

## E3 relevance

Pi can schedule `drive` calls without making the harness a platform scheduler. DSH has separate jobs, schedule and workflow packages plus typed tool scheduling. These are candidate primitives for bounded task claiming, but neither reference proves Health's proposed swarm topology, fairness, blackboard semantics or evaluation benefit. E3 should require a fixed fan-out/claim budget, explicit task event log, bounded retries, idempotency policy, and per-topology metrics. No E3 implementation is started by this audit.

## E5 relevance

DSH presets/bundles and static identity mechanisms can inform candidate variant packaging; Pi/DSH introspection can inform comparing explicit configurations. Neither repository implements self-evolution in the research sense of evaluation → selection → promotion → rollback across episodes. Extensibility is not self-evolution. E5 would still need source/data/config identity, held-out evaluation, safety gates, promotion policy, rollback and replay identity. No learned policy, plugin mutation or promotion loop is started here.

## Rejected designs

- Replacing `ComponentRegistry` with arbitrary runtime plugin discovery: rejected as a trust, hash and replay regression.
- Treating Pi's deployment sandbox disclaimer as a Health permission model: rejected because M9 requires explicit decision and enforcement status.
- Using model-generated compaction in the frozen M10.1 path: rejected because it weakens deterministic projection and replay.
- Turning DSH's broad event/plugin vocabulary into a global Health middleware bus: rejected until one observed ownership/failure problem requires it.
- Treating upstream session entries, tool output or prompt resources as medical Evidence or automatic Memory: rejected by Health's authority boundaries.
